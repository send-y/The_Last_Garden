# Варианты инструментов — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Варианты топора, кирки, мотыги и ведра добавляются через данные и работают в командах игрока, поддерживаемых работах NPC и UI без веток по новому ID.

**Architecture:** Каталог готовит возможности один раз. Симуляция проверяет конкретный физический экземпляр и его состояние. UI получает возможности, ёмкость и хват из того же каталога.

**Tech Stack:** Godot 4.7, GDScript, JSON, Windows/PowerShell.

**Spec:** [Согласованная подготовка контента](../specs/2026-10-10-content-extensibility-design.md), раздел «Предметы и действия». [Перенос еды](../../implementation/item-food-properties-2026-10-11.md) выполнен. Поля и интерфейсы ниже — следующий предлагаемый контракт.

## Global Constraints

- Базовые числа сохраняются: ведро 2, расход одного полива 1, увлажнение 1440 игровых минут. Темп/добыча ресурсов, потребности, дальность, стройка, карта и минутная частота не меняются; обязательный молоток не вводится.
- Нужен выбранный физический экземпляр игрока либо принадлежащий этому NPC переносимый экземпляр. Запас/тег сами по себе работу не разрешают. Смена даже на другую копию той же модели сохраняет прежний сброс начатой добычи; обычный отказ до работы не расходует ресурсы, время, энергию и RNG.
- Сейв остаётся версии 36: прежние `item_id`, `instance_id`, `state.charges`, location и `initiative_job.tool_id`. Определения и диагностики в сейв не записываются.
- Горячие запросы — bool/число из подготовленных данных, без JSON, полного копирования определения и поиска всего каталога. Проверка ссылок источников проводится при подготовке контента, не каждый тик.
- В обычную игру новые модели не добавляются. Fixtures: `test:axe_variant`, `test:pickaxe_variant`, `test:hoe_variant` с прежними возможностями; `test:bucket_variant` ёмкости 4; `test:deprecated_axe` для совместимости. Ёмкость 16 — отдельный граничный тест, не баланс игры.
- Износ, скорость/качество, массовые действия, мультитулы, новый выбор дел NPC и переименование `FirstNightContent` вне пакета. FPS/стресс-прогоны не возобновляются; игровой `first_night_save.json` не является тестовым файлом.
- Существующий пакет еды сохраняется. Автор запросил локальный коммит между задачами 5 и 6: фиксировать только подготовленный пакет еды/инструментов и его проверки, без посторонних файлов и без пуша. Предварительный коммит всего дерева не выполнять.

## Данные и совместимость

Формат предметов 5, `food_schema_version: 1`, `tool_schema_version: 1`. Форматы 3/4 принимаются по прежним правилам, но новые `tool`/`deprecated` в них отвергаются. Базовые модели получают явные данные, без восстановления возможностей по ID.

~~~json
"tool": {"actions": ["chop", "clear_bush"], "grip": "shaft"}
"tool": {"actions": ["water"], "grip": "carry", "water_capacity": 2}
~~~

Версия 1 поддерживает четыре набора действий: `[chop, clear_bush]`, `[mine]`, `[till]`, `[water]`; порядок несущественен, дубликаты запрещены. `tool` необязателен; с ним нужны `instance_based: true`, `max_stack: 1`, валидный набор и хват `shaft` для первых трёх / `carry` для воды. `water_capacity` требуется только для воды: конечное целое 1–16. Неверные типы/поля, действия, комбинации, версии, ёмкости и повторные ID дают ошибку с файлом, ID и полем; ошибочное определение не получает возможности.

`state.charges` — целочисленный счётчик дискретных использований ресурса экземпляра; у ведра единица означает полив. Поле само по себе не даёт водной возможности. Только для валидного водного инструмента: отсутствующее/нечисловое/bool/дробное/не конечное значение → 0, корректное целое ограничивается `0..capacity`; другие поля сохраняются. Создание и загрузка используют одну нормализацию.

Опубликованные ID сохраняются вместе с полным определением и ассетами. Устаревание — `deprecated: true` (необязательный bool); оно не удаляет существующие вещи, возможности и ID задания NPC. Удаление/переименование опубликованного ID требует отдельной миграции. Активные рецепты, источники и пулы **не могут ссылаться на устаревший ID**; это проверяемое правило, описанное ниже. Использование предмета из сейва и наличие в старом складе источником создания не считаются.

Иконки пока используют точные `icon_state_paths`: у ведра 4 явно описаны 0–4, у граничного примера — 0–16. Изменение ёмкости требует описания состояний. Долевые иконки и предпочтения моделей NPC отложены.

**Каталог:** `item_tool_profile(id: String) -> Dictionary` (отдельная копия/{}), `item_tool_supports(id: String, action: String) -> bool`, `item_tool_capacity(id: String) -> int` (иначе 0), `item_tool_grip(id: String) -> String` (обычный предмет — carry), `item_is_deprecated(id: String) -> bool`.

## Проверка ссылок источников

Единый запрос `FirstNightContent.validate_item_references(refs: Array[Dictionary]) -> Array[String]`. Запись: `{source_path, owner_id, field, item_id}`. Неизвестный либо устаревший ID — ошибка с этими четырьмя значениями. Это проверка явных полей схем, не поиск любых похожих строк в JSON.

Обязательные подключения:

- `recipes.json`: ключи `inputs` и `outputs`, до включения рецепта в `CraftingCatalog`.
- `first_night_objects.json`: `collect_rules.*.item_id`, до включения правила добычи.
- `crops.json`: `seed_id` и `product_id`, до включения культуры; это источники семян/урожая.
- Встроенные источники: начальные физические предметы/склад в `world_rules.gd` и дополнительное выпадение шишек в `resource_system.gd`. Их декларации выделить в единственные используемые исполнителем данные/константы и проверить при подготовке симуляции; не держать отдельный несвязанный список «для проверки».
- Общего каталога loot/generation pools сейчас нет. Будущий загрузчик обязан передавать все ID записей этому же валидатору **до активации пула**. В текущем тесте проверить нормализованную ссылку пула; не утверждать, что несуществующий загрузчик уже подключён.

Загрузчик отвергает ошибочное правило/рецепт/культуру, а ошибочный встроенный источник не выдаёт предмет. Сохранённые экземпляры и задания не проверяются как новые источники. Существующие порядки и числа сохраняются, только проверки совместимости добавляются.

## Структурированные диагностики загрузки

`WorldSimulation.item_load_diagnostics: Array[Dictionary]` — производное поле вне `state`. Элемент `{id: String, count: int, reason: String}`; причины `unknown_item_definition` и `not_instance_based`. Количество — число отброшенных физических записей. Группировать по ID+причине, порядок — первый встреченный случай; список очищается перед каждой нормализацией экземпляров и не накапливает прошлые загрузки.

`get_item_load_diagnostics() -> Array[Dictionary]` возвращает глубокую копию. `_normalize_item_instances` собирает данные, затем `ItemLoadDiagnostics.warning_text(row: Dictionary) -> String` формирует сообщение для одного `push_warning` на строку. Не добавлять диагностики на минутном тике. Основной тест сравнивает список; лёгкий тест форматтера проверяет ID/count/reason без захвата вывода Godot. Предупреждение сообщает о фильтрации, но не восстанавливает отсутствующее определение.
